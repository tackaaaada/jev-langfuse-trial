# 検証知見と公開時の注意

この文書は、合成の10件データと固定の長文ペアで行ったJev・Langfuseの検証から得られた知見をまとめたものです。結果は小規模な動作確認・設計検討の材料であり、モデルの精度、独立性、費用対効果を一般化するものではありません。

## 現時点で確認できたこと

1. **Jevによる一次評価は実装できる。**
   TypeSafe SDKから、回答と期待回答を入力としてJevを呼び出し、その応答をLangfuseのObservationとScoreに記録できた。

2. **Noul、Choice、Scoreは評価軸に合わせて定義できる。**
   今回は正確性だけに絞り、Noulを意味的一致、Choiceを主な正確性上の差分、Scoreを差分の重要度として定義した。各評価軸に必ず3種類すべてが必要なわけではない。二値判断にはNoul、互いに排他的な主因の分類にはChoice、順序付きの大きさにはScoreを使う。

3. **今回の10件では、JevとLLM-as-a-Judgeに大きな判定差は見られなかった。**
   Jev、JevありGPT-4o、JevなしGPT-4oは、いずれも人手ラベルと9/10件で一致した。Jevあり／なしのGPT-4oの最終booleanは全件同一だった。これは小さな合成セットでの観測であり、一般的な一致率や精度を意味しない。

4. **Jev結果をLangfuseの管理Evaluatorへ参考情報として渡せる。**
   `finalize-answer`のmetadataにJev結果を保存し、Evaluatorの`variableMapping`で`{{jev_correctness_assessment}}`へ割り当て、プロンプトへ展開している。metadataに保存するだけではEvaluatorには渡らず、マッピングとプロンプトの両方が必要である。

5. **Jevをどの程度参考にしているかは、まだ結論づけられない。**
   `unsupported-shipping-claim`ではJevのChoiceとScoreが追加情報を問題視した一方、GPT-4oはJevあり・なしの両方でtrueになった。GPT-4oがChoice・Scoreを機械的に採用していないことは分かるが、Noulもtrueだったため、Noulから独立している証拠にはならない。

6. **現在確認できた範囲はtext-to-textである。**
   入力はテキストの回答と期待回答だけであり、画像・音声・動画を含むマルチモーダル評価は検証していない。対応可否、入力形式、精度、費用は別途確認が必要である。

7. **Jevの結果は将来のゲート候補になるが、LLM-as-a-Judgeの判定をそのまま本番ブロック条件にはしない。**
   同期呼び出しのJevは、確率・Choice・Scoreに基づくルーティングや人手レビュー対象の選定に使える。一方、自動ブロックを含む判定にLLM-as-a-Judgeを使うには、評価基準・プロンプト・出力形式・閾値を用途に合わせて設計し、誤検知・見逃し・例外処理・人手レビューを人手ラベルで校正する必要がある。

## 実験から得た設計上の注意

### 意味的一致と事実性は別の評価対象

`unsupported-shipping-claim`では、期待回答にない追跡番号・置き配の情報を追加した。人手では、運用条件を根拠なく追加しているためfalseとした。一方、JevのNoulとGPT-4oは、既存の送料・配送日数・送料無料条件と矛盾しないとしてtrueにした。

これは「期待回答の意味を保持したか」と「期待回答にない事実を加えなかったか」が別の要件であることを示す。追加情報を常にfalseにするのか、非矛盾なら許容するのかを、用途ごとにプロンプトと例で明示する必要がある。

### Choiceは単一の主因、複数エラーの完全な列挙ではない

Choiceは一つのラベルだけを返す。`changed-relationship`は人手では関係変更と見なしたが、Jevは矛盾・制約変更を主因に選んだ。どちらもbooleanのfalseには整合するが、分類をEvaluatorの振り分けに使う場合にはカテゴリの重なりが問題になる。

複数のエラーを独立に検出したい場合は、主因Choiceだけに依存せず、論点ごとのNoulを追加するか、Choiceの確率分布を人手レビュー用の補助信号として扱う。

### Scoreはbooleanの部分点ではない

Scoreは定義した順序尺度に対する期待値である。今回の0〜3は差分の重要度を表し、true／falseの中間値ではない。Noulの閾値とScoreの閾値を同じ意味で扱わない。

### 「参考情報」を検証するには介入実験が必要

Agent-as-a-Judgeに、アプリケーションが記録した入力・出力・metadata・tool callsを渡して処理を評価させることは有用である。ただし、Judgeが自動的にアプリケーション内部を観測できるわけではなく、観測できる範囲は評価対象Observationに明示的に記録・マッピングした情報に限られる。管理Evaluatorの出力理由や実行トレースを観察しても、Jevへの依存度を証明することはできない。検証には、同じ回答・期待回答・Evaluator版を使い、次の条件を明示して比較する。

1. Jev情報を渡さない条件
2. 実際のJev情報を渡す条件
3. 意図的に反転・変更したJev情報を「合成の対照」と明記して渡す条件

各条件を複数回実行し、最終booleanだけでなく理由、Jevとの一致率、人手ラベルとの混同行列を比較する。対照用の偽Jev情報を本番トレースへ混在させない。

## 公開前のセキュリティ確認

### 運用で決めること

- 回答・期待回答・Jev応答・Langfuseの判定理由を外部サービスへ保存してよいか、データ分類と利用目的を定める。
- 個人情報、認証情報、顧客データ、社外秘の文章は送信前にマスキングまたは除外する。
- Langfuseプロジェクトの閲覧権限、OpenAI接続、APIキーの保管先、保存期間、削除手順を組織の方針に合わせる。
- 公開前に、公開予定のGit履歴を含めて秘密情報スキャンを再実行する。もし過去にキーをコミットしていた場合は、ファイルの削除だけでなくキーの失効・再発行が必要になる。
- 公開リポジトリの利用条件を示すライセンスを選ぶ。ライセンスはまだ追加していない。
